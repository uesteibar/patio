# Development and verification environment

These recipes let an agent build and check the POC without a human. They run the real patio processes (exchange, gatekeepers, CLI, MCP server) in isolated instances. They use test doubles by default, and live smokes only when you ask for them and have budget left.

Run every recipe from the worktree root. `just` calls Bun through `mise exec`, so the pinned Bun in `mise.toml` is always the one used.

## Recipes

| `just setup` | `mise install`, then `bun install --frozen-lockfile`. Safe to run twice. | package registry | setup |
| `just worktree <name> [branch]` | Creates `worktrees/<name>` (on `branch`, created when missing; default `<name>`), copies the main checkout's `.env` into it with mode 600, and runs `mise install` and `bun install`. `bunfig.toml` sets `env = false`, so Bun never loads that `.env`: tests, `check`, `verify` and every non-live script run without its values (`test/dev/env-isolation.test.ts` fails otherwise); live recipes read the keys explicitly. | package registry | setup |

| `just check` | `tsc --noEmit` and the full `bun test` suite: the upstream suite plus the tests under `test/dev/` and `test/fakes/`. | `just up <agents...>` | Starts an instance: a fake GitHub, an exchange on a free port configured for it (database in the instance), a fake Jev that finds everything benign (the gates always run), and one patio per agent. Each agent's file is `agents/<handle>.yaml` in its home; a spec can add more agents on the same computer (`extra`). | loopback only | deterministic |
| `just cli <id> <agent> -- <args>` | Runs the real `patio` CLI as that agent in that instance, for example `just cli 261108-ab12 alice -- who`. The exit code is patio's own. | loopback only | deterministic |
| `just down <id>` | Stops the processes listed in that instance's manifest, and no others. | none | deterministic |
| `just env <id> <person>` | Prints shell exports for a new person in that instance (a `PATIO_HOME` inside the instance root, the instance's server and fake Jev), to set up by hand with `patio join <link>` (`eval "$(just env $ID dave)"`). The patio that join starts is not in the manifest: stop it with `kill $(cat $PATIO_HOME/patio.pid)`. | none | deterministic |
| `just scenario <name\|all>` | Starts a fresh instance, runs a scripted scenario through real CLI processes, checks expectations, writes a transcript and stops the instance. | loopback only | deterministic |
| `just mcp-probe <id> <agent>` | Starts `patio mcp` as that agent. Then another agent of the instance sends it a heads-up and the client closes it with `dismiss` and checks it is dismissed; and sends it a question, which the client declines with `reject` and a reason (a second `reject` fails with `already_rejected`), and the sender's `wait` gets the reason. Prints JSON. | loopback only | deterministic |
| `just browser-check` | Headless host Chromium through `playwright-core` loads a local page and saves a screenshot under `.verify/browser/`. | loopback only | deterministic |
| `just browser-join` | Headless Chromium, in a fresh instance: Jorge's coding agent runs `patio join <link> --no-wait` on a fresh home (no terminal) and prints one link; in the browser Jorge signs in through the fake GitHub and lands on the one screen (*Your agent jorge-team (Claude Code in …) wants to join team*, Confirm and Decline); Confirm covers the computer, the agent and the join; the flash and the confirmed screen say *Tell your agent you are done* (and that it still has to finish the setup while its file is incomplete), and the agent's second run (with the three answers) finishes; his Agents page says the three answers as sentences with the `patio rules` command that changes them. Then Bob, with two agents on one computer, opens the Agents page: one card per agent (tool, folder, workspace chips, the coding tools and the `patio connect` command for each, its one set of rules, with no tab per workspace, and a **Guide** link to the agent's guide, the text its coding tool reads with the MCP tool `guide`); a workspace is taken out and put back. Then, with his laptop off, Jorge's agent runs the same join on jorge-mac: the screen says *jorge-team lives on your other computer jorge-laptop (last seen just now)*, that the laptop has no other agent and is revoked too, and has one action, **Move jorge-team to this computer**; Move confirms it there, and the agent's second run ends with the line about teammates trusting the new keys. Last, Alice removes Jorge from team, and his agent's join from another computer lands on a screen with the refusal, Decline and no Confirm. Screenshots go to `.verify/browser/join-<timestamp>/`. | loopback only | deterministic |
| `just browser-channels` | Headless Chromium checks the read-only channel and DM views in a fresh instance: the channels empty state, a channel join request as an approval card, a broadcast with two replies grouped under it, a DM with its answer, no compose box, and the workspace's channel list. Screenshots go to `.verify/browser/channels-<timestamp>/`. | loopback only | deterministic |
| `just browser-gates` | Headless Chromium checks the gates' approval cards in a fresh instance with the fake Jev: the empty state, an incoming message held by Bob's input gate and an outgoing reply held by his output gate (who, what, the grant rule, Jev's probabilities, the editable draft), that another signed-in user sees nothing held, approving the incoming one, and editing and sending the outgoing one, which Alice receives. Screenshots go to `.verify/browser/gates-<timestamp>/`. | loopback only | deterministic |
| `just browser-keys` | Headless Chromium checks the keys-changed card and the Devices page in a fresh instance: Alice pins Bob's keys, the exchange's directory swaps them (Bob's agent now on his second device), her next question is held; the card shows the pinned and new fingerprints, the note that a device addition looks the same, and Block / Trust the new keys; trusting releases the question. Screenshots go to `.verify/browser/keys-<timestamp>/`. | loopback only | deterministic |
| `just browser-activity` | Headless Chromium checks the Activity page and the configuration-error banner in a fresh instance with the fake Jev: Bob's gates deliver, reject and hold Alice's messages (he approves the held one) and he replies; the page lists the five decisions newest first, a row opens to its probabilities, Bob's own reply shows its text and Alice's held message does not, and the verdict filter narrows the list. Screenshots go to `.verify/browser/activity-<timestamp>/`. | loopback only | deterministic |
| `just browser-invites` | Headless Chromium checks the invite links and default channels in a fresh instance: Alice marks `#general` default (the Default label, Make default / Not default), creates a 7-day, 5-use link (listed with its uses, expiry, Copy and Revoke); the server's invite page (*@alice invited you to team · 1 agent*, the **Copy prompt** block with the install line and the `patio join … --folder "$PWD" --connect --no-wait` command, naming no coding tool, which Copy prompt puts in the clipboard and the check saves as `invite-prompt.txt`, and its step 3 with the three questions (a screenshot of that step); the command for your own terminal; **Open in the patio app** with a `patio://join/` link); Carol's second agent asks to join from no terminal and her Needs you page shows one card (*carol-side (Pi in …) wants to join team*), which one click confirms; a revoked link's page says so (410). Screenshots go to `.verify/browser/invites-<timestamp>/`. | loopback only | deterministic |

To add a scenario, write a module in `scripts/scenarios/` that exports a `Scenario` and add it to `SCENARIOS` in `scripts/scenario.ts`. `just verify` picks it up. An agent spec's `grants` (in the old `rules.yaml` shape) and its `agentConfig` (the old `agent.yaml` shape: `agent`, `cwd`, `model`, `effort`, `in_place`) are written to its file, `agents/<handle>.yaml`; `extra` adds more agents of the same person on the same computer. Every instance runs a fake Jev process (in the manifest, stopped by `down`); a scenario's `jev` fixture replaces the benign default, and `jev: null` runs none. Every gatekeeper gets its URL (`PATIO_JEV_URL`) and a fake key, also after a restart; an agent spec's `env` can override them. The transcript includes the gate audit logs it reads, the held cards it sees, and how many requests the fake Jev received. `t.start` runs a CLI command in its own process group so a scenario can kill it mid-way, as a crash would.

Every process of an instance (exchange and gatekeepers) reads a test clock, `PATIO_TEST_CLOCK=<root>/clock` (an offset in milliseconds, 0 until written), and looks for what expired every 200 ms (`PATIO_SWEEP_MS`). `t.advanceClock(ms, label)` moves it forward, so expiry scenarios do not sleep. `t.stopExchange()` and `t.startExchange()` make an outage (same port and database), and `t.startAgent(handle, env, { connected: false })` starts a gatekeeper while the exchange is down.

`just doctor` prints:

- The installed versions of the project SDKs.

## Isolation rules

- **One root per instance.** Everything for an instance lives in `.dev/instances/<id>/`. Each agent's `PATIO_HOME` is `<root>/<agent>/`, so its socket, rules, device keys and inbox stay there. The exchange runs with `--db <root>/exchange.db`, so its mailbox never touches `~/.patio/exchange.db`. Both `.dev/` and `.verify/` are gitignored.
- **No user home.** A home outside the instance root is refused, and so is `~/.patio`. This is checked when an instance starts, when a manifest is read, and before every `just cli`. Inherited `PATIO_*` variables are dropped from every process an instance starts, so a developer's own `PATIO_HOME` cannot leak in. Every process gets `PATIO_NO_NOTIFY=1`.
- **Ports from the OS.** The exchange starts with `--port 0`, and the port it prints is written to the manifest. Two instances can run at the same time; `test/dev/instance.test.ts` runs two side by side.
- **Identity per instance.** Each instance runs its own fake GitHub (`test/fakes/fake-github.ts`) with its own client id and secret, and the exchange is configured for it only. Inherited `GITHUB_*` variables are dropped, so an instance can never reach the real GitHub. Each gatekeeper's web app listens on a free port on 127.0.0.1.
- **The service scenario touches your systemd user manager.** `service` writes `~/.config/systemd/user/patio-watch-test-<instance id>.service`, enables and starts it, and removes it in a `finally` (disable, delete, daemon-reload, reset-failed), then checks nothing is left. The unit runs `patio watch` against the instance's gatekeeper only.
- **Stop only what you own.** `manifest.json` records each PID with its `/proc` start time. `just down` signals a PID, and the process group it leads (so agents a daemon started stop too), only when that PID still belongs to the same process.
- **No real adapter in check or verify.** The join's answer preflight and `patio status` start the agent's real ACP adapter. Tests that join with a preset tool set `PATIO_NO_PREFLIGHT=1` (scenarios and the browser checks run with `PATIO_NO_SERVICE=1`, which skips it too); `test/answer-env.test.ts` and `test/join-tools.test.ts` run the preflight with the fake ACP agent, from the service's minimal environment. The real adapters run only in `just probe-answer`.
- **Desktop notifications stay off.** `PATIO_NO_NOTIFY=1` in every test and script; `test/questions.test.ts` checks the notification commands (`notify-send`, `terminal-notifier`, `osascript`) without running them.
- **No server judge unless asked.** An instance's server gets the fake Jev as its judge only when the scenario sets `serverJudge` (`server-judge`); otherwise `/judge` answers 503 there, and a gatekeeper without a key fails closed (`gate-jev-down`). Instances turn on, in the web app, what an agent spec's `rules.yaml` widens (`auto_answer`, `actions` lists), as its owner would.
- **No inherited Jev key.** Every `TYPESAFE_*` variable is dropped from what an instance process inherits, so a key in the developer's environment never reaches a deterministic instance. A gatekeeper gets a Jev key only through its agent spec's `env`: the fake key in scenarios and `browser-gates`, the real one only in the live recipes (`smoke-acp`, `smoke-gates`, `dogfood`, `adversarial`, `actions`, `responders`).
- **Secrets.** `TYPESAFE_API_KEY` is read from the main checkout's `.env`: the parent of `git rev-parse --path-format=absolute --git-common-dir`, so `/home/devbox/code/uesteibar/patio/.env`. `just worktree` copies it into each new worktree (mode 600); `bunfig.toml` sets `env = false`, so Bun loads it nowhere, and `test/dev/env-isolation.test.ts` fails if a test process sees one of its names. Doctor reports whether `TYPESAFE_API_KEY`, `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` are present, by name. Only `smoke-jev` and `smoke-gates` read the TypeSafe key and only `smoke-github` reads the GitHub pair; none prints them. `smoke-gates` hands the key to Bob's gatekeeper through its environment; the manifest records only the variable's name. Tests override the path with `PATIO_POC_ENV_FILE`.

`manifest.json` holds:

- `id`, `root`, `created_at`
- `revision` and `dirty`
- `github`: the fake provider's PID, process group, start time, log, port, URL, and the instance's fake client id and secret
- `exchange`: PID, process group, start time, log, port, URL and database path
- `jev`: the fake Jev's PID, process group, start time, log, port, URL, fixture file and request log (`jev.requests.jsonl`), or null
- for each agent: handle, owner login, workspace, home, socket, web app URL, the names of extra env variables (not their values), PID, start time and log
- `workspaces`: name, id and the agent whose owner is its admin
- `stopped_at`, once the instance is stopped

## Test doubles

Neither double is live evidence.

- **Fake ACP agent** (`test/fakes/fake-acp-agent.ts`). It speaks ACP over stdio with `@agentclientprotocol/sdk` and follows a JSON fixture:
  - `modes`: the modes it reports, or `null` to report none.
  - `steps`: tool calls to attempt, each with a permission request.
  - `reply`: the reply text, with `{{step}}` placeholders for step results.
  - `delayMs`: how long it works before replying (for leases and concurrent consumers).
  - a step's `whenPrompt`: a regex; the step runs only when the prompt matches it (an agent that acts only when told it may; `just actions --fake` uses it).

  A step with `permission: false` acts without asking, the way an agent's own setup lets it. A step that asks acts only when the client's answer selects an allow option, so a refused edit really does not touch the disk. Patio rejects every request, so with patio only steps that do not ask ever act. It logs the initialize capabilities, `session/new` (cwd and `_meta`), any mode change, the prompt it was offered, and each permission request and answer, as JSON lines in the `--log` file. Patio reaches it through `agent.yaml` (or `patio answer --agent`) whose `agent:` is the command. Patio splits that command on spaces, so its paths must not contain any.
- **Fake Jev** (`test/fakes/fake-jev.ts`). A local HTTP server for `POST /v1/systemone`:
  - Bearer auth, required `model`, `state` and `questions`.
  - `noul`, `choice` and `score` answers in the API's response shape, with `usage` and `x-typesafe-request-id`.
  - Request bodies compressed with zstd or gzip.

  Answers come from a fixture keyed by question id. An answer can depend on a regex over the state. A question with no fixture answer gets a 400 that names it, unless the fixture has a `default` answer (instances use one, since every message gets a prompt-injection check). As a process (`--fixture`, `--log`, `--api-key`) it prints its address and logs each request as a JSON line. `box` questions and image assets are not implemented. `@typesafe-ai/sdk` reaches the fake through its `baseURL` option; a gatekeeper reaches it through `PATIO_JEV_URL`. The gates' question ids are `injection`, `action`, `secrets` (always), `deny_<i>`, `allow` and, for a list of allowed actions, `action_ok_<i>` on the way in, and `secrets`, `deny_<i>` and `posture_<i>` on the way out (see `scripts/scenarios/gates.ts` and `scripts/scenarios/actions.ts` for fixtures).
- **SDK workaround.** Under Bun 1.4.4, `@typesafe-ai/sdk` 0.7.0 fails every response with `ERR_BODY_ALREADY_USED`. It locks the body of the response and of its clone, and Bun then reports the body as used. Pass `fetch: bunSafeFetch` from `src/jev.ts` (re-exported by `scripts/lib/jev.ts`), which returns a buffered response. The gatekeeper's Jev client, the fake tests and `smoke-jev` use it.

## Live smokes

The paid smokes are opt-in. Each stops before any network call unless all of these hold:

- `--yes-live` is given. Otherwise it exits 4.
- `.dev/budget.json` has budget left. Otherwise it exits 5.
- `smoke-jev`, `smoke-gates` and `smoke-acp`: the key is present. Otherwise it exits 2.

Budget is reserved before the paid call, so a crash does not give a free retry. The limits come from `docs/poc/execution.md`:

- `codex_acp`: 40 per day, and 59 in total (`codex_acp_build_total`): the 19 runs of batch 1 plus the 40 of batch 2 (`docs/poc/batch-2.md`, which sets no daily cap for Codex). Raised from 20 and 20 in increment 7. Set the total to `null` once the build is over.
- `jev`: 600 requests per day (raised from 300 for 8 Nov 2026 in the increment 8 acceptance, for the live checks of increments 9 and 10).
- `claude_acp`, `pi_acp`, `hermes_acp`: 15 runs each in total (`<kind>_total`), the batch-2 limits for Claude Code, Pi and Hermes on Haiku 5.5 low. No daily cap.

Edit `limits` in `.dev/budget.json` to change them.

A message stopped on the sender's side (exit non-zero from `ask`) is recorded as not sent.
  - **Budget.** It reserves 18 jev units (one per message) before anything is sent. Each message costs at most one Jev request; a DLP block or a structured-rule rejection costs none. It reports how many requests it made.
  - **What it records.** Sender, verdict, rule, reason, the action check (policy, requested, allowed action), each question's probability, latency and model, from Bob's audit log, with the expected verdict for each message. `.verify/live/gates-<timestamp>/` gets `table.md`, `report.json` and Bob's `audit.jsonl`.
  - **Pass condition.** Every message the gates sent to Jev got an answer. Whether each verdict matched the expectation is reported, not a pass condition.
  - **Since increment 9** every outgoing message also gets the always-on `secrets` question. The increment 10 rerun (8 Nov 2026, `.verify/live/gates-2026-11-08T23-12-49-949Z/`) had 18 of 18 verdicts as expected; the good reply scored 0.02 on `secrets` and was sent.

## Reading the evidence

`just verify` writes `.verify/<UTC timestamp>-<short rev>/`:

- `summary.md`:
  - the overall PASS or FAIL, the revision and whether the tree was dirty
  - a table of every step with its label (deterministic or live), whether it is required, exit code, duration and result
  - links to each step's log and to the evidence it produced: scenario transcripts and the browser screenshot
  - dependency versions
- `manifest.json` holds the same data in machine-readable form: revision, dirty flag, versions, and for each step the command, exit code, duration, label and evidence paths.
- `logs/NN-<step>.log` holds the full stdout and stderr of each step.

A scenario transcript (`.dev/instances/<id>/transcript.md`) lists:

- every CLI call with its arguments, exit code, stdout, stderr and duration
- every expectation, as a checkbox
- gatekeeper stops and starts, and exchange restarts, in the order they happened (scenarios use `stopAgent`, `startAgent` and `restartExchange` from `scripts/lib/instance.ts`; a restart keeps the home, keys, inbox, port and database, and appends to the same log)
- for scenarios that scan the exchange database, which files were read and whether any plaintext was found
- the last lines of the exchange and gatekeeper logs

Next to it, `result.json` holds the checks as JSON.

What counts as what:

- **Deterministic.** Everything except the live smokes. These results use the fakes (fake GitHub, fake ACP agent, fake Jev) or a `run` rule and prove the patio plumbing and the gates' thresholds, not model behaviour.
- **Live.** Only the live recipes (`smoke-acp`, `smoke-jev`, `smoke-gates` and `rules-live` in `verify --live`; `dogfood`, `adversarial`, `actions` and `responders` on their own), labelled `live` in the summary. A summary without `--live` says that no live smoke ran.
- **Dirty trees.** Evidence from a dirty tree is marked as dirty. Rerun on a clean commit before you rely on it.
